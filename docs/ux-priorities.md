# UX priorities and measurement plan

Updated October 20, 2026. This is the decision layer for the existing journey audit, not an implemented redesign. It combines the [original Chrome capture findings](ux-findings.md), [historical telemetry reference](telemetry-reference.md), [fresh Incognito technical audit](technical-audit.md), [runtime telemetry evidence](runtime-telemetry.md), and [full assignment brief](../Founding%20Product%20Take-Home%20b4381b607554839287ad8137811d7133.md). The original captures stop at blank Basic Info. Supplemental payment observations became available after David personally created an account; no payment action was performed by the agent.

The strongest immediate design opportunities are **mobile matching and task hierarchy**, followed by **cost and commitment clarity across reservation and payment**. Current production already sends granular fit and matching events: validate and use them before adding duplicates. Fit's historical loss still does not establish a broken experience. The eventual product outcome remains the first **completed** visit.

## Ordered priorities

| 1. Put useful matching choices first | At 390 × 844 CSS pixels, the initial match page is 3,901 pixels tall. The numerical losses above are **historical same-session non-progression**, not causal abandonment or estimated recoverable patients. Mobile screenshots are responsive Chrome captures, not physical-device proof. Sticky-header placement artifacts in some full-page captures are not established product defects. All eight routes also emit automatic `$pageview` according to the brief. Conditions, insurance, and needs action events are documented, but the supplied funnel uses page reach for those stages. Repeated page events and disclosed cross-route events must not become extra conversions. Current `portal.onboarding.match.reservation_created` and `portal.provider.reservation.created` coexist for one reservation: choose a canonical event or deduplicate the business outcome. Batch referrer routes can follow a navigation, so use event semantics and ordering instead of assigning every event to that referrer. The [telemetry reference](telemetry-reference.md) contains the historical canonical mapping.

## Measurement and validation

1. **Retain the historical comparison.** Reproduce ordered same-session milestones with explicit denominators, event ordering, and deduplication. Add new outcome views alongside it instead of silently changing its unit.
2. **Separate fit outcomes using existing data.** Validate `question_visit_id`, `submission_id`, and the existing question-event sequence. Request restricted aggregate breakdowns for eligible decisions, service-fit exits, technical failures, and unresolved journeys, with device cohorts. Measure eligible completion → conditions separately. The observed eligible path alone does not validate every branch; no subsequent event does not establish why someone stopped.
3. **Support continuation.** Define a restricted opaque journey identifier and attempt identifiers; associate journeys with accounts only when established. Propose seven-day intake continuation and 30-day first-visit completion as initial windows, subject to review against observed scheduling lead times. Report only mature cohorts for each window and distinguish resumed journeys from same-session progression. Neither identifier by itself proves a unique patient.
4. **Segment before claiming a mobile win.** Capture viewport/device class and experience version. Compare equivalent eligibility, coverage, and availability cohorts through an appropriately controlled rollout or experiment. Use task success, comprehension, time/effort, validation failures, and reservation failures alongside progression; a small usability study establishes usability evidence, not conversion lift.
5. **Minimize analytics data.** Use an explicit event/property allowlist: version, stage, deduplication ID, restricted opaque journey/attempt IDs, viewport class, approved error categories, elapsed-time buckets, and result/availability counts. Exclude diagnosis, medication, answer values, names, contact details, birth date, free text, raw API errors, and recordings/transcripts. Question identity plus branching or exit state can itself reveal a sensitive answer: keep clinical routing detail in restricted operational data and expose only approved aggregates for analysis. Pseudonymous care-seeking data is not anonymous. Mask form fields and avoid blanket replay/autocapture.
6. **Verify operational truth.** Use synthetic scenarios to test eligible and excluded routing, interrupted/resumed journeys, no availability, stale slots, reservation failure, validation recovery, pending benefits, payment failure, and changed/missed visits. Confirm event ordering and deduplication against authoritative service outcomes. These are prototype/measurement acceptance cases, not permission to exercise sensitive actions in the live flow.

There is no observed successful payment, confirmed appointment, or completed visit. This document recommends future work; the prototype remains pending David's feedback on the audit.
